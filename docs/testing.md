# 验证与协议测试

在项目根目录执行 `npm run typecheck`、`npm test`、`npm run check:api` 和 `npm run build`。`check:api` 校验 OpenAPI 格式并自动比对后端路由，接口新增、删除或改名时，漏更新文档将导致检查失败。

`npm run test:e2e` 自动构建并在 `localhost:5173` 启动生产版本，在桌面、平板、手机三种 Chromium 视口验证页面和交互。首次运行先执行 `npx playwright install chromium`。浏览器测试使用独立 `data/e2e` 数据库和测试管理员，不会修改日常使用的邮箱数据；若 5173 已被常驻服务占用，可执行 `E2E_PORT=5174 npm run test:e2e` 使用独立端口。

浏览器验证包含真实登录、API 令牌的使用与撤销、交互文档，以及多账号筛选、HTML 净化与沙箱隔离、正文图片自动加载、附件下载和发信失败后保留草稿。图片检查须验证 CID 内嵌图片与 HTTP(S) 外部图片的实际解码结果（如 `naturalWidth > 0`），同时检查无须点击加载、切换邮件取消未完成的内嵌图片请求、外部图片请求使用 `no-referrer`，以及邮件自带的脚本 / 事件无法执行、HTML 沙箱不授予同源权限。内置测高脚本仅通过随机 CSP nonce 放行；需验证其他来源、错误 token 或非法高度的消息无法改变阅读器尺寸。邮件界面交互使用明确的测试响应；真正的 IMAP / SMTP 收发由下述协议测试独立验证。PWA 测试从首次安装开始，清除 HTTP 缓存后断网，检查应用静态界面可以启动且 API 响应从未进入 Service Worker 缓存。

紧凑列表回归使用多封长主题与长摘要邮件，检查桌面 / 平板 / 手机的行高、一屏可见邮件数量、横向溢出和星标按钮的触按区域；打开邮件后的窄列表也需检查主题截断和行高。测试测量实际渲染结果，避免仅验证 CSS 声明。

详情阅读回归使用长纯文本与 HTML，验证侧栏、标题栏、操作栏及底部导航的实际尺寸；在正文区域通过滚轮和手机触摸滚动，顶部文件夹标题、邮件数量与操作栏应固定在视口顶部，主题及发件人信息随正文移出视口；宽屏列表与第二条分隔线始终位于标题栏下方且不超出底部。HTML 正文按实际高度展示，图片加载后会重新测量；宽表格仅在正文内横向滚动。切换邮件从顶部开始，返回列表恢复原位置；平板同时覆盖竖屏与横屏。

桌面三栏回归检查未选中邮件时仍显示阅读区、两条分隔线的实际拖动与键盘调整、刷新后的宽度保留、双击恢复、窗口缩放的阅读区最小宽度及窄屏隐藏分隔线。拖动越过邮件正文 iframe 后仍应持续响应并正常释放。使用模拟 Google 安全提醒与推广邮件验证内联样式、样式表、背景、边框、字号、按钮及表格宽度的实际渲染结果；邮件 CSS 不应修改宿主界面或可信测高容器，图片须保持比例且不被固定高度裁切。

顶部信息密度回归需测量工具栏是否位于同一标题栏内、正文起始位置及发件人 / 主题 / 收件人的三行布局。将桌面阅读区拖至 320 像素、手机缩至 320 像素，验证长主题与长地址不覆盖日期和按钮；回复、转发、删除和标记始终可见；手机返回按钮移至第二行。标记菜单里的已读 / 未读与星标，以及更多菜单里的安装和提醒入口可用，Escape 能关闭并恢复焦点。正文 iframe 的默认底色应与阅读区一致，原邮件内部明确指定的卡片与品牌颜色须保留。

邮箱导航回归使用两个账号、不同语言与路径的常用目录、同名自定义目录及不可选择的容器，验证统一目录按用途合并、账号目录按真实路径隔离、空目录可访问及分组独立折叠。打开或刷新页面后，统一分组展开、各账号分组折叠；手动改变三组状态再刷新，仍须恢复默认状态。侧栏顶部无品牌区域，直接提供写邮件入口。切换账号 / 目录须清空搜索、重置分页和阅读选中状态，手机快捷入口保持当前账号范围；断开正在查看的账号后回到统一收件箱，不保留原账号的真实目录路径、搜索或正文。侧栏底部仅一个设置入口，无管理员卡片。登录、密码和 API 令牌鉴权继续验证。

账号编辑回归验证配置回填、密码不回填 / 留空保留、SMTP 独立凭据开关与新密码必填、验证失败保留草稿并重试、保存后卡片和导航更新、仅身份变化才重置目录，以及 Google OAuth 仅更新名称 / 颜色并提供重新授权入口。后端使用隔离数据和受控连接模拟，验证失败不覆盖原配置、身份变化清理本地缓存、旧邮件 ID 隔离和配置编辑 / 同步 / 邮件操作串行化；不会修改真实邮箱配置或发送真实邮件。

安装入口回归检查未收到安装事件时按钮仍可用、HTTP 地址显示 HTTPS 限制、手动指引可关闭并再次打开；通过模拟 `beforeinstallprompt` / `appinstalled` 验证原生安装调用、取消、异常、确认安装及完成后的按钮状态。这些模拟事件验证界面流程，不能替代系统实际安装。上线 HTTPS 后还需在真实 Android / 桌面浏览器点击按钮完成安装并从应用图标打开；iPhone / iPad 从 Safari 的分享菜单添加到主屏幕后打开，再单独验证提醒授权及后台推送。局域网 HTTP 的快捷方式不作为完整 PWA 安装通过的依据。

推送注册后端回归位于 `server/test/push-subscriptions.test.ts`，随 `npm test` 执行。使用临时数据库、合成订阅及受控 DNS / Web Push 模拟，验证注册接口不执行 DNS 查询或私有 / 保留 IP 预检，也不发送实际通知；公网地址、TUN Fake-IP、私有地址、混合 IPv4 / IPv6 和 DNS 失败场景均不影响注册，且与 `ALLOW_PRIVATE_MAIL_HOSTS` 的值无关。HTTPS、受信浏览器推送服务域名、端口及订阅密钥格式仍须有效，登录鉴权与来源校验继续生效。20 设备额度已满时，同一设备重复登记仍能更新密钥且不增加记录；新增设备被拒绝，已有订阅归属与删除范围不会被覆盖。

浏览器提醒回归通过模拟 `Notification`、Service Worker、PushManager、VAPID 公钥和 API，在桌面 / 平板 / 手机验证已有本地订阅的完整流程。登录、回到前台、网络恢复和 Service Worker 切换应自动补登记已有且公钥匹配的订阅，不自动申请许可或创建订阅；公钥变更应引导到设置重新开启。进入“设置 → 应用与提醒”后须检查登记，等待服务端响应时显示检查状态并禁用按钮；首次注册失败应显示错误，不能仅因浏览器存在订阅就显示已开启。点击“开启提醒”重试须复用匹配的原订阅，服务端确认成功后才显示开启；关闭并重新打开设置应幂等登记，不再创建本地订阅。关闭提醒时，先确认服务端删除成功，再取消本地订阅并恢复可开启状态。测试通过延迟响应检查中间状态，使用的地址、密钥与会话均为测试数据，无真实推送。

可用 `E2E_PORT=5174 npm run test:e2e -- --grep 'existing push subscription'` 定向执行上述三端提醒流程。注册成功只表示服务端已保存订阅；真实送达需在 HTTPS 安装后的设备上，保留现有 TUN / 代理环境，结合系统通知权限与新邮件同步另行验收。

新邮件同步回归位于 `server/test/mail-notifications.test.ts`，用隔离 IMAP / notify 模拟验证 INBOX 自己首次成功建立基线，其他目录先成功不算收件箱基线，UIDVALIDITY 重置不提醒旧邮件。基线建立后新到邮件即使已被其他客户端标为已读仍触发一次，未读数不被伪造；后续目录部分失败、断线、INBOX 的 STATUS 失败或 FETCH 不完整后恢复，均检查提交与通知顺序。SSE 与 notify 的同批 `notificationId` 一致，不同批次不同，异常收尾仍复用原 ID。

隔离 Worker 回归需验证前台 SSE 与后台 Push 同 ID 只提醒一次、同账号稳定 tag 的新批次使用 `renotify`，以及重复消息仍正常更新角标。IndexedDB 去重仅保存不含业务内容的 UUID 和时间，保留 7 天、最多 128 条；检查不持久化正文、endpoint 或凭据，存储不可用时仍能显示通知。须分别模拟 open、getAll、写事务永久等待及迟到回调，确认各路径在 500 毫秒限时后降级，第二封和测试通知继续、迟到历史不覆盖内存、写入超时不阻塞队列；角标 API 永久等待也不能阻塞展示及事件完成。

当前用户已确认真实设备收到测试通知，自动新邮件送达仍待用户验收。正常轮询默认为 60 秒，以已登录 `/api/v1/config` 的 `pollingInterval` 为准，验收需等候一次轮询；首次历史同步或 UIDVALIDITY 重置安静建立基线，不能作为漏通知判据。结合设备系统通知、角标及服务器 `New-mail push accepted` / `New-mail push failed` 日志检查；日志不包含 endpoint、密钥或正文，accepted 仅表示服务商接受。上述模拟回归不等同于真实新邮件送达已验证。

转发回归使用合成邮件与模拟附件响应，验证原邮箱、空收件人、主题去重、可编辑原文及附件移除；源附件首次下载失败时保留草稿且不发送，重试成功后原附件与手工附件的 Base64 内容正确。转发不带旧线程头，回复仍保留；删除调用移动至回收站接口。

执行 `npm run test:mail` 可使用真正的 TLS IMAP / SMTP 连接进行集成测试，需要 Docker 和 OpenSSL。脚本自动启动固定版本 GreenMail 沙箱、生成临时 localhost 证书、通过 `NODE_EXTRA_CA_CERTS` 信任该测试证书，并在结束后删除容器与临时文件。不会关闭证书验证，也不会发送到外部邮箱。

协议测试验证两个账号的连接、统一与单账号查询、SMTP 发送、IMAP 同步、MIME 附件内容、远端已读和星标、移动回收站、已发送副本以及断开连接后远端邮件保留。账号编辑另覆盖名称 / 颜色保留缓存、独立 SMTP 启用及取消、错误 IMAP / SMTP 密码验证失败时配置和缓存不变，以及更换 IMAP 登录身份后旧邮件 ID 隔离、重新同步成功且双方远端邮件均保留。沙箱不替代 Gmail 真实账号的 OAuth / 应用专用密码验收；Google 授权需要申请人自己的 OAuth 客户端配置及同意授权。

参考：[GreenMail 官方文档](https://greenmail-mail-test.github.io/greenmail/)。

触屏平板回归以 1280×800 与 1097×600 的 coarse pointer 视口，通过 Chromium 实际触摸事件拖动两条分隔线，检查三栏可见、拖动后实际尺寸变化、正文最小宽度、保存和刷新恢复；缩至 768 像素时隐藏分隔线并保持无横向溢出。

返回导航回归检查邮件切换不累加阅读层级、后退返回列表、前进恢复邮件，设置关闭和前进恢复，以及写信时返回触发原草稿确认、取消保留正文。独立 PWA 根页首次返回保留应用并显示提示，连续第二次返回允许退出；普通标签页能返回真正的上一页，连续刷新不增加保护历史条目。

后台刷新稳定性回归使用延迟的列表 API 与合成 SSE 同步 / 新邮件事件，检查原邮件 DOM 不卸载、不出现加载占位，列表滚动位置保持，完成后新增邮件正常显示。初次打开、切换目录、筛选、搜索和分页按当前范围加载，不将前一范围的邮件显示到新列表。刷新失败保留当前列表和重试入口。

通知测试与角标回归模拟当前设备订阅及投递响应，检查未登记不可测试、当前 endpoint 提交、临时失败重试、成功只提示“服务已接受”，关闭提醒清除测试提示。后端用临时数据库和受控 Web Push 验证投递对象、所有者隔离、限频、过期清理、错误脱敏与总未读数，不发送真实通知。浏览器用合成账号和 SSE 验证总未读数字 / 标题 / setAppBadge 更新、切换账号仍保留总计、平板 / 窄栏铃铛收起时更多按钮与提醒菜单保留可见数字、0 和退出登录清除、不支持或拒绝 Badging 静默；隔离 Worker 实际执行构建后的 Service Worker，检查 push 中合法数字、零值、缺失 / 非法字段及 API 失败均不影响可见通知。自动测试不能替代真实设备的系统角标与推送送达验收。


推送投递参数回归需验证普通与测试均为 `urgency:high`、首次 `TTL:3600`（队列重试为剩余 TTL）、`contentEncoding:aes128gcm`，同批次共享 topic、不同批次不相互替换；测试 UUID 与正常提醒经过同一 Worker 路径。Worker 更新回归见 `tests/worker-update.spec.ts`，模拟 register 返回前已经发出 updatefound、当前 installing / waiting、回前台重新检查和失败后重试；不得强制刷新导致草稿丢失。


后台可靠性回归见 `server/test/push-outbox.test.ts`：真实 SQLite 队列、模拟 provider，覆盖同事务 stage 回滚、重开数据库恢复、永久失败 / 过期 / 8次上限、4并发、退避抖动与 Retry-After、订阅更换 / 取消及旧410不误删新密钥、停机等待在途任务、整次发送 12 秒总超时与迟到结果不回写数据库、有界保留和日志脱敏。邮件同步测试另覆盖 INBOX 提交后停止其他目录、重开 Store 时 pending 已存在，stage异常回滚缓存与基线。应用层回归验证重试保持 UUID / topic 并用当前未读数。所有发送均模拟。

账号排序回归覆盖完整 owned ID 验证、原子保存、改名保留顺序、新账号追加、重开数据库持久与跨用户隔离；前端覆盖保存失败保留调整、重试成功、刷新导航和发件选择保持顺序，以及侧栏实际紧凑间距。发件名回归使用真实 MIME Composer + mock SMTP 检查默认 / 自定义名称、Unicode引号及发件地址和 SMTP envelope 不变；三端检查切换邮箱默认名称、编辑保留草稿和回复 / 转发，拒绝邮件头换行注入，不发送真实邮件。锁屏指引与返回系统设置后检查现有订阅的测试使用合成权限、无授权弹窗或新订阅。

通知内容回归验证主题、纯文本正文摘要、发件人及多封数量在 SSE 与 Push 中一致，同 ID 去重仍有效；Unicode / emoji 超长字段保持完整字符，Web Push JSON 小于 4 KiB，预览失败仍通知。IMAP 模拟验证每批只为最高新增 UID 下载有界文本部件，不读附件 / 历史、下载失败或超时可继续、事务 stage 与最终详情一致。`npm run test:mail` 的真实 TLS GreenMail 沙箱另检查单段 GB2312 quoted-printable、HTML-only base64、附件排在正文前的 MIME，提取后不设置 Seen，不产生完整 body/source 缓存。

`tests/notification-appearance.spec.ts` 以模拟 SSE / Service Worker 检查通知主题与摘要、旧事件兼容、版本化蓝色图标、透明单色 badge、manifest 与静态预缓存。浏览器与系统的最终通知布局、Chrome 来源归因、已安装桌面图标更新时间仍需真机核对，自动验证不声称移除系统控制的浏览器标识。

连续加载回归在桌面 / 平板 / 手机检查下滑追加、加载中不重复请求、错误原地重试、到尾停止、切换邮箱 / 目录 / 筛选 / 搜索重置、旧响应不覆盖新范围；模拟 SSE 在多批列表中新增 / 删除，检查按 ID 去重、保留已加载范围、选中与滚动、不闪出加载占位。多端回归使用同一账号两个独立会话 / 设备和另一个所有者，验证新邮件发往全部本人订阅、失败独立处理、不串到其他用户；已读 / 星标 / 移动及账号 / 发信事件广播本人两条 SSE，更新当前阅读元数据不重载 iframe。设备必须各自开启提醒，模拟验证不代表真实设备通知权限已授权。
